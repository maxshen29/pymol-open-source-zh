# Internationalization (i18n)

PyMOL's desktop interfaces can now display English or Simplified Chinese,
with a centralized catalog system that makes adding languages and keeping
translations consistent cheap.

## Status

| Capability | State |
| --- | --- |
| English (source) | built-in, always available |
| Simplified Chinese (`zh_CN`) | shipped (`data/i18n/zh_CN.json`, 900+ strings) |
| Language switch at runtime (Qt) | yes (`Display → Language`), both directions |
| Language switch at runtime (Tk) | menu entry sets the language; applied on next start |
| Command line switch | `pymol --lang zh_CN` |
| Environment switch | `PYMOL_LANG=zh_CN pymol` |
| Persisted choice | `~/.pymol/i18n.json` (written by the GUI menu) |
| Default-language detection | OS UI locale → English |
| Live re-translation on switch (Qt) | yes, menus + toolbar + dialogs + tooltips |
| Right-click menu | yes, rendered as a native **Qt** menu (see below) |
| Internal GUI (object list, HUD, popups) | yes — embedded **Noto Sans SC** via FreeType (requires a C++ rebuild) |

> **Right-click menus.** PyMOL's C++ internal GUI paints popup menus with a
> GLUT bitmap font that only covers ASCII/Latin-1, so Chinese labels would show
> as `??????`. `modules/pmg_qt/qt_context_menu.py` therefore renders the menu
> with Qt (which has Unicode fonts) instead. Since the picked atom lives in C++
> (`I->LastPicked`) and is not exposed to Python, the Qt menu shows the generic
> "Main Pop-Up" (what PyMOL shows on empty-space right-click); the
> object/atom-specific menus are not reproduced. It is only used in the default
> 3-button mode and can be switched off:
>
> ```
> qt_context_menu 0     # back to the native PyMOL menu
> qt_context_menu 1     # Qt menu (default)
> ```
>
> or `PYMOL_QT_CONTEXT_MENU=0` in the environment.

## Architecture

```
modules/pymol/i18n.py           core translator (stdlib only, standalone)
modules/pmg_qt/i18n_qt.py       Qt widget/menu localizer (duck typed)
modules/pmg_qt/qt_context_menu.py  Qt-rendered right-click menu
modules/pmg_qt/pymol_qt_gui.py  Qt front end wiring + language menu
modules/pmg_tk/skins/normal/    Tk menubar wiring
data/i18n/en.json               source-language catalog (key registry)
data/i18n/zh_CN.json            Simplified Chinese translation
tools/i18n_lint.py              catalog validation (CI gate)
testing/tests/i18n/             unit tests (no PyMOL build required)
```

The core module is pure standard library and can be imported standalone, so
translation works the same in the Qt GUI, the Tk GUI, and headless scripts,
and the whole subsystem is unit-testable on a machine without the C
extension.

## How translation works

Every user-visible string stays written in English in the source. At render
time it is passed through `pymol.i18n.tr()`:

```python
from pymol import i18n
print(i18n.tr("File"))            # 文件  (when the language is zh_CN)
print(i18n.tr("Welcome, {name}", name="Ada"))
```

Lookup order for a key: **requested language → English catalog → the literal
English text**. A missing translation never raises and never breaks the UI;
the string simply stays in English.

Two kinds of keys are accepted in catalogs:

* **English source strings** (the common case, e.g. `"File"`), which let
  legacy code be migrated incrementally and are always safe.
* **Dotted symbolic keys** (e.g. `"dialog.builder.title"`) for new code; these
  must also be listed in `en.json` with their English text.

## Catalog format

`data/i18n/<code>.json`:

```json
{
  "meta": {
    "language": "zh_CN",
    "native_name": "简体中文",
    "english_name": "Simplified Chinese",
    "source_language": "en",
    "fallback": "en",
    "version": "1.0"
  },
  "strings": {
    "File": "文件",
    "Open...": "打开..."
  }
}
```

`en.json` is the source language and key registry. A value may also be a
plural mapping `{"one": ..., "other": ...}`.

## Language resolution

Highest priority first:

1. `i18n.set_language()` (the GUI language menu),
2. `--lang <code>` on the command line,
3. `$PYMOL_LANG`,
4. the language saved by a previous session (`~/.pymol/i18n.json`),
5. the operating system's UI locale,
6. English.

An unsupported locale silently falls back to English.

## Adding a language

1. Copy `data/i18n/zh_CN.json` to `data/i18n/<code>.json`.
2. Edit `meta.language`, `meta.native_name`, `meta.english_name`.
3. Translate every entry in `strings` (keep `{placeholders}`, `%s`, and the
   trailing `...` exactly).
4. Run `python tools/i18n_lint.py` — it must report `0 error(s)`.
5. Optionally add a display name entry to `_DEFAULT_NAMES` in
   `modules/pymol/i18n.py` and any alias to `LANGUAGE_ALIASES`.

## Extracting and checking strings

* `tools/i18n_lint.py` validates JSON, duplicate keys, `meta`, placeholder
  parity and empty translations; `--coverage <inventory>` reports how much of
  an extracted GUI inventory is translated.
* `testing/tests/i18n/` exercises the core and the Qt localizer with the stock
  `unittest` runner:

  ```
  python -m unittest discover -s testing/tests/i18n -p 'test_*.py'
  ```

## Internal GUI (C++ / OpenGL)

PyMOL's C++ internal GUI draws the object list, the popup menus and the HUD
with `TextDrawStr` / `TextDrawChar` (`layer1/Text.cpp`). The bundled bitmap
fonts (`FontGLUT*`) only cover Latin-1, so Chinese would render as `?`.

The fix (already applied in `layer1/Text.cpp` and `layer4/PopUp.cpp`):

* `layer1/FontCJK.h` — an embedded **Noto Sans SC** subset (7,265 characters:
  ASCII, Latin-1, CJK punctuation, GB2312, and every character used by the
  translation catalogs). Generated by `tools/gen_font_header.py`; the font is
  SIL Open Font License 1.1.
* `TextInit()` registers it as font id 19 and sets `Default_CJK_ID`, which
  `TextDrawStr` / `TextDrawStrAt` now use. Both renderers already decode UTF-8
  (`FontGLUT.cpp:next_utf8_character`, `FontType.cpp:CheckUnicode`).
* `PopUp.cpp` now decodes UTF-8 per code point and advances by 2 cells for
  CJK; the popup width is computed in character cells (2 for CJK).
* `FontType.cpp` had to be made null-safe: the vector-font renderer read
  `RenderInfo` fields unconditionally, but the Ortho overlay passes
  `nullptr` (bitmap fonts don't need it). Both `info->` dereferences are now
  guarded, otherwise using a TTF font in the internal GUI crashes.

Because this is a **C++ change**, it only takes effect after rebuilding the
`_cmd` extension (see `scripts/build_windows.ps1` or
`.github/workflows/build-wheel.yml`). Regenerate the font asset with:

```
python tools/gen_font_header.py --font "C:\Windows\Fonts\Noto Sans SC (TrueType).otf"
```

## Scope and roadmap

* Covered: the shared menu bar (Qt and Tk), the Qt toolbar and dock chrome,
  the Qt dialogs and their tooltips (localized on first show), the language
  selector, the command line / environment switches, the right-click
  "Main Pop-Up" (native Qt menu), **the C++ internal GUI popup menus**
  (object list `S/H/L/C/A` buttons) and **the internal GUI HUD**
  (`Mouse Mode`, `Buttons`, `Keys`, `Picking`, `Frame`, `State`, …) — see
  [`docs/images/internal-gui-chinese-popup.png`](images/internal-gui-chinese-popup.png)
  and [`docs/images/internal-gui-chinese-hud.png`](images/internal-gui-chinese-hud.png).
* HUD strings are hard-coded in C++, so a table is generated from the catalog
  by `tools/gen_hud_header.py` into `layer1/HudTr.h` (UTF-8 escaped so the
  compiler's source charset does not matter) and looked up by `TextTr()`;
  `$PYMOL_LANG` (kept in sync by `pymol.i18n.set_language`) selects Chinese.
* Remaining: object names are ASCII-only by PyMOL's own validation, so the
  object list cannot show Chinese names. Keyboard abbreviations
  (`Shift`, `Ctrl`, `CtSh`) and mode mnemonics (`Rota`, `MovZ`, …) stay
  English on purpose.
* Translators wanted: the Chinese catalog is a first-quality pass; see
  `data/i18n/zh_CN.json` and open a PR to improve wording.
